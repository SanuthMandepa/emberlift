# Security Design

Feature ID: 001-core | Governed by Constitution Article III

We are writing authentication ourselves rather than adopting a managed provider.
That is a deliberate choice made by the product owner, and it means the burden of
getting it right sits here. This document is the contract. Anything not written down
here is not implemented, and anything implemented differently from here is a defect.

---

## 1. Threat Model

| # | Threat | Likelihood | Impact | Control |
|---|---|---|---|---|
| T1 | Credential stuffing using passwords breached elsewhere | High | Account takeover | Argon2id, breached password rejection (FR-002), per account rate limit (FR-008), lockout |
| T2 | Database dump exposes passwords | Low | Catastrophic, reputational | Argon2id with per user salt. A dump yields no usable passwords |
| T3 | Cross site scripting steals the session | Medium | Account takeover | httpOnly cookies (FR-007), strict CSP, React escaping, no `dangerouslySetInnerHTML` |
| T4 | Cross site request forgery | Medium | Unwanted state change | SameSite=Lax cookies plus an origin check on every mutating request |
| T5 | Stolen refresh token replayed | Low | Persistent access | Rotation with family revocation on reuse (FR-006) |
| T6 | Horizontal privilege escalation, reading another user's logs | Medium | Privacy breach, breaks FR-062 | Repository layer injects `user_id` into every query. Enforced by a lint rule and a test |
| T7 | SQL injection | Low | Total compromise | Drizzle parameterized queries only. Raw SQL requires review sign off |
| T8 | Enumerating registered emails | Medium | Privacy, phishing target list | Identical response and timing for known and unknown emails on register, sign in, and reset (FR-009) |
| T9 | Invite link brute force | Low | Unwanted connection | 128 bits of entropy, hashed at rest, expiry and use limits (FR-060) |
| T10 | Secret leaked into git history | Medium | Full backend compromise | `.gitignore` from commit one, secret scanning in CI, pre-commit hook |
| T11 | Dependency supply chain compromise | Medium | Arbitrary code execution | Pinned lockfile, `npm audit` gate in CI, Dependabot |
| T12 | Push endpoint abused to spam a user | Low | Nuisance | Subscriptions bound to an authenticated user, delivery idempotency key, per user send cap |
| T13 | Denial of wallet on free tiers | Medium | Service suspension, breaks NFR-005 | Rate limits on all unauthenticated routes, request size caps, no unbounded queries |
| T14 | Malicious or oversized user content | Low | Stored XSS, storage abuse | Zod length caps on every text field, output escaping, no HTML accepted anywhere |

## 2. Password Storage

**Algorithm: Argon2id.** Chosen over bcrypt for memory hardness against GPU attack,
and over scrypt for its better studied side channel resistance.

Parameters, meeting OWASP guidance, with headroom for serverless memory limits:

```
memoryCost = 19456 KiB (19 MiB)
timeCost   = 2
parallelism = 1
hashLength = 32
salt = 16 random bytes, unique per user, generated by the library
```

Rules:

1. The encoded hash string includes algorithm, version, parameters and salt. It is
   stored whole in `users.password_hash`, so parameters can be upgraded later.
2. On a successful sign in, if the stored hash uses weaker parameters than the
   current configuration, it is transparently rehashed with the plaintext already in
   memory.
3. A plaintext password is never logged, never placed in an error message, never
   included in a stack trace, and never sent to any third party service.
4. Verification is constant time, provided by the library's `verify` function.

**Password policy (FR-002)**: minimum 12 characters. No composition rules, since
they produce weaker passwords in practice. Checked against the Have I Been Pwned
range API using **k-anonymity**: only the first 5 characters of the SHA-1 hash leave
our server, so the password itself is never transmitted. If that API is unreachable,
fall back to a bundled list of the 10,000 most common passwords, and never block
registration on a third party outage.

## 3. Session Management

Two credentials, different lifetimes, different jobs.

### Access token

- Format: JWT, signed **EdDSA (Ed25519)** via JOSE. Not HS256, so the verification
  key can be separated later if we split services.
- Lifetime: **15 minutes**.
- Claims: `sub` (user id), `sid` (device session id), `role`, `iat`, `exp`, `iss`, `aud`.
- Carries no personal data beyond the user ID. A JWT is signed, not encrypted, and
  anyone holding it can read the payload.
- Transport: cookie `__Host-at`, `HttpOnly; Secure; SameSite=Lax; Path=/`.

### Refresh token

- Format: 32 random bytes from a CSPRNG, base64url. Not a JWT. It is a bearer
  secret, and its authority comes from the database row, not from a signature.
- Storage: **SHA-256 hash only** in `refresh_tokens.token_hash`. A database dump
  cannot be used to mint sessions.
- Lifetime: 30 days, sliding.
- Transport: cookie `__Host-rt`, `HttpOnly; Secure; SameSite=Strict; Path=/api/auth`.
  The narrow path means it is not sent with ordinary API calls, so it has far less
  exposure than the access token.

### Rotation and replay detection (FR-005, FR-006)

Every refresh consumes the presented token and issues a new one in the same family.

```
present token T
  ├─ T not found                → reject, no information disclosed
  ├─ T.used_at IS NOT NULL      → REPLAY DETECTED
  │                               revoke the entire family,
  │                               sign out every device,
  │                               write a security_event,
  │                               email the user
  ├─ T expired                  → reject, require sign in
  └─ T valid and unused         → mark used, issue T' in the same family,
                                  return new access + refresh
```

This is the standard OAuth 2.0 BCP rotation scheme. A stolen token is usable at most
once, and the theft is detected the moment either party uses it again.

### Invalidation

`password_updated_at` on the user is compared against the access token's `iat`. A
password change instantly invalidates every outstanding access token without needing
a revocation list.

## 4. Authorization

**Rule: authorization is enforced in the data layer, never in the UI and never in a
route handler alone.**

Every user owned read goes through a repository function whose signature makes the
actor mandatory:

```ts
// The actor is not optional. There is no overload without it.
export async function getSession(actor: Actor, sessionId: string) {
  return db.query.sessions.findFirst({
    where: and(eq(sessions.id, sessionId), eq(sessions.userId, actor.userId)),
  });
}
```

Enforcement:

- A custom ESLint rule forbids importing the `db` client outside `src/db` and
  `src/lib/repositories`.
- A missing resource and a forbidden resource return the **same** 404 response
  (FR-012). Returning 403 confirms the resource exists, which leaks information.
- An integration test attempts, for every user owned resource type, to read another
  user's record and asserts a 404. This test is required to pass in CI.

## 5. Transport And Browser Hardening

Headers set on every response:

| Header | Value |
|---|---|
| `Content-Security-Policy` | `default-src 'self'; script-src 'self' 'nonce-{random}'; style-src 'self' 'nonce-{random}'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'; object-src 'none'` |
| `Strict-Transport-Security` | `max-age=63072000; includeSubDomains; preload` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), payment=()` |
| `Cross-Origin-Opener-Policy` | `same-origin` |

No `unsafe-inline` and no `unsafe-eval`. Nonces are generated per request in
middleware. If a library cannot run without `unsafe-inline`, we replace the library.

## 6. Input Validation

Every route handler begins the same way, with no exceptions:

```ts
const parsed = Schema.safeParse(await req.json());
if (!parsed.success) return badRequest(parsed.error);
```

- Zod schemas are shared between client and server. The client copy is for user
  experience. **The server copy is the security control.**
- Every string has a maximum length. Every number has a range. Loads are bounded at
  0 to 1000 kg, reps at 0 to 1000. An unbounded field is a defect.
- Request bodies are capped at 1 MB, except the sync endpoint at 5 MB.
- All IDs are validated as UUIDs before they reach a query.

## 7. Rate Limiting (FR-008, T13)

Postgres backed fixed window counters. Redis is not free, and our volume does not
need it.

| Endpoint | Limit | Key |
|---|---|---|
| `POST /api/auth/register` | 5 per hour | IP hash |
| `POST /api/auth/login` | 5 per 15 min | **User account**, plus 20 per 15 min per IP hash |
| `POST /api/auth/reset` | 3 per hour | Email hash, plus IP hash |
| `POST /api/auth/refresh` | 60 per hour | Device session |
| `POST /api/invites` | 10 per day | User |
| Authenticated writes | 300 per minute | User |

Keying the login limit on the account rather than only the IP is what actually stops
distributed credential stuffing. Lockout responses are identical in shape and timing
to a wrong password, so the limiter cannot be used to enumerate accounts (T8).

## 8. Secrets

| Secret | Where it lives |
|---|---|
| `DATABASE_URL` | Vercel environment variables, GitHub Actions secrets |
| `JWT_PRIVATE_KEY` / `JWT_PUBLIC_KEY` | Ed25519 keypair, Vercel environment variables |
| `VAPID_PRIVATE_KEY` / `VAPID_PUBLIC_KEY` | Public key is shipped to the client by design. Private key is server only |
| `RESEND_API_KEY` | Server only |
| `CRON_SECRET` | Shared between GitHub Actions and the reminder endpoint. The endpoint rejects any request without it, compared in constant time |
| `IP_HASH_SALT` | Server only. Makes stored IP hashes non-reversible |

`.env.example` documents every variable with a fake value and is committed.
`.env` is git-ignored from the first commit (Constitution III.2). CI runs secret
scanning, and a pre-commit hook blocks obvious key patterns.

## 9. Privacy (Constitution Article VI)

- Sharing defaults to off. A new account has zero outbound shares (FR-062).
- IP addresses are stored only as salted hashes, for rate limiting and suspicious
  login detection. Never in plaintext.
- No third party analytics, no advertising, no session replay, no heatmaps (NFR-008).
- Account deletion hard deletes all rows within 24 hours, including in the audit log
  where the row is user identifying (FR-011).
- Full data export in JSON on demand (FR-006 in spec, Constitution VI.1).

## 10. Verification Gates

The following must pass before v1 ships. Each is a blocking gate, not a checklist.

1. `npm audit` reports no critical or high severity vulnerability.
2. The cross user access integration test passes for every user owned resource type.
3. A refresh token replay test proves the whole family is revoked.
4. Automated header check confirms every header in section 5.
5. `/security-review` run against the full diff, with every finding resolved or
   explicitly accepted in writing.
6. Manual review confirms no secret exists anywhere in git history.
7. A password reset flow test confirms tokens are single use and expire.
